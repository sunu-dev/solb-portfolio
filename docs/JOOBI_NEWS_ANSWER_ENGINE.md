# 주비 뉴스·답변 엔진 설계 v1

작성: 2026-11-17. 상태: v1 로컬 구현·검증 완료, 실API 검증 승인 대기·운영 적용 전. 범위/한계는 마지막 절 참조.
범위: 질문별 뉴스 검색·선별·근거 평가·프롬프트 조립·답변 검증. 새 유료 서비스/상시 수집 서버 도입 없음.
제품 기준: JOOBI_EXPLANATION_PRINCIPLES.md. 목표는 질문의 궁금증 해결이며 기사 수·답변 길이·검사 수가 아님.

## 1. 확인된 결함과 아직 모르는 것
- assistantArticleSources.ts의 검색/fetch/채택 도메인에 뉴스핌·매일경제가 없음. 시선AI11/16 뉴스핌 원문은 이 경로에서 근거가 될 수 없음.
- 회사와 시장 검색을 항상 병렬 배정(각 검색1회, 합계최대2회/본문4회). 회사 근거가 부족해도 시장에 예산이 배정됨.
- route.ts withoutReporting은 article/publication 하나의 존재만 검사. 시장 기사만으로도 회사 원인 질문의 근거 부족 전용 처리가 해제됨.
- needsArticleSupplement는 회사/시장 범주 존재를 보며, 질문에 답할 실제 사건·시점·관련성을 충분히 판정하지 않음.
- 프롬프트에 근거 없는 확인 과제 금지가 이미 있지만 사용자 사례에서는 그런 과제가 출력됨.
- 해당 요청의 실제 검색결과/탈락사유/timeout은 확보하지 못함. 위 구조적 결함과 해당 요청 전체의 실행 원인을 구분.

## 2. 처리 흐름
질문 해석 → 검색 계획 → 후보 수집 → 원문·사건 선별 → 근거 충족 판정 → 필요시 제한 내 보완 → 답변 계약 → 생성 → 검증 → 응답.
검색과 답변 생성을 분리한다. 검색 모델이 쓴 요약을 원문 증거로 삼지 않는다.

### 질문 계약 QuestionContract
- intent: price_cause / company_update / concept / comparison / followup.
- entity: 정규 종목ID, 사용자에게 보일 회사명, 검증한 별칭·옛이름, 거래소. 동명이인 불명확하면 먼저 좁힘.
- period: 시장 시간대·거래일 기준 시작/끝, 비교 기준일, 가격 확인시각.
- cutoff: 사용자가 요구한 시점. 과거 사건을 지금 설명하는 retrospective와 당시 알 수 있던 정보만 묻는 as_of 구분.
- observedMove: 가격 소스가 확인한 방향/변화. 질문이 '급등'이라 해도 검증 전 사실로 고정하지 않음.
- requiredClaims: 해당 질문에 필요한 주장(사건, 회사 연결, 관찰 가격 등). 일반 개념 질문은 뉴스 검색 생략.
- 공개 검색에는 종목·날짜·공개 사건 키워드만 전달. 사용자 원문/대화/보유내역 전송 안 함.

## 3. 검색 계획과 적응형 예산
초기 목표는 기존 회사 질문의 총 검색 상한2회/본문4회 안에서 품질을 개선하는 것. 횟수·시간은 코드 전역 예산으로 강제하고 실제 provider tool 사용량과 대조한다. 숫자는 실측 후 조정할 초기값이지 최적값이 아니다.

1. 가격원인/회사근황: 회사명+날짜+중립적 사건검색을 우선. 상승·하락 단어만으로 검색해 반대 근거를 배제하지 않음.
2. 첫 결과를 평가하고 두 번째 검색의 목적을 하나 선택:
   - 회사 결과 없음 → 별칭/옛이름/종목코드+원어명으로 보완.
   - 제목 단서는 있으나 원문 실패 → 같은 사건의 접근 가능한 다른 원문 탐색.
   - 회사 사건 있지만 연결 불명확 → 사건 키워드와 회사 관계 또는 공식 발표 확인.
   - 업종/정책 사건으로 연결됨 → 그 업종/정책의 공통 배경 검증.
   - 회사 사건 충분함 → 남은 검색 생략. 시장 기사를 반드시 채우지 않음.
3. 시장 질문은 시장→필요 업종 순서. 비교 질문은 비교 대상 균형을 우선.
4. 후보 단계는 최대12개까지 메타데이터만 정리, 본문은 중복 제거 후 상위 후보부터 최대4건. 새 사건 또는 반대 증거 확보 여지가 없는 반복 열람 금지.
5. 검색·본문 전체 wall-clock 초기 목표28초, 최대 동시본문2개. 기존 병렬 검색보다 느려질 수 있으므로 p95 실측 필수. 예산/시간이 끝나면 확보한 근거로 종료, 백그라운드 무제한 검색 금지.
6. 근거 충족 또는 남은 예산으로 해소할 수 없는 부족이면 조기 종료. 자동 재질문/중복 차감 없음.

## 4. 출처 정책
- 검색 발견 범위와 본문 취득 허용 범위를 분리. 품질 확인된 언론/거래소/공시/회사 IR 목록을 버전 관리.
- 뉴스핌 등 누락된 매체는 실제 API의 원문 접근 가능성·이용 제한·본문 파싱 검증 후 추가. 웹브라우저 열람 성공이 provider 접근 성공을 보장하지 않음.
- 신뢰도와 접근 가능성을 별도 필드로 관리. 유명 매체라도 반복 접근 실패 시 대체 출처로 전환.
- 신규 도메인은 자동 신뢰하지 않음. 출처 식별 불가·콘텐츠 농장·검색최적화 재가공 요약은 핵심 근거에서 제외.
- 공식 발표는 계약/실적 사실 확인에 우선. 회사 홍보를 독립된 주가 원인 증명으로 취급하지 않음.
- 제목·검색 snippet은 후보 단서만. 유료벽/접근제한 우회 없음. 직접 HTTP fetch를 추가하면 private IP/redirect/SSRF·응답크기 제한을 별도로 구현.
- 기사 내용은 비신뢰 데이터. 도구 실행/시스템 지침으로 해석하지 않음.

## 5. 기사 선별과 사건 묶기
하드 필터 후 순위화한다. 점수가 높다고 원인 증거가 되지는 않는다.

하드 필터: 종목 식별 오류, 대상 시점과 무관, 원문 없음, 날짜 확인 실패, 출처 불명, 중복.
날짜가 불명확한 자료는 당시 원인 근거에서 제외하되 보완검색 단서로 보존한다.

초기 후보 순위(정수합, 확률 아님): 회사·대상 일치0~3, 사건시점 일치0~3, 질문 관련성0~3, 출처·직접성0~2, 새 정보0~2. 중복/사건 무관은 감점이 아니라 제외. 가중치는 고정 평가셋으로 조정.
- 본문 보존은 단어 빈도 대신 사건 주체·행동·대상·날짜·조건·부정/한계를 한 묶음으로 발췌. 원문 위치/근거ID 포함.
- 사건묶음: 주체+행동+대상+사건일+원출처. 동일 보도자료 전재5건을 독립 근거5개로 세지 않음.
- publishedAt, eventAt, fetchedAt, priceCutoff를 별도로 저장. 장 마감 뒤 보도가 이전 사건을 설명할 수 있지만, 뒤에 발생한 사건을 낮 상승 원인으로 쓰지 않음.
- 관련성 분류: 회사 사실 / 보도된 주가 연결 / 관련 사건·가능한 영향 / 공통시장배경 / 무관.
- 충돌하는 날짜·계약 여부·규모는 삭제해 매끈하게 만들지 말고 충돌 상태로 전달.

## 6. 질문별 근거 상태 EvidenceAssessment
기존 withoutReporting 단일 boolean을 대체한다. 회사·시장 기사 유무는 보조 정보일 뿐이다.

| 상태 | 필요 근거 | 허용하는 답변 |
| --- | --- | --- |
| reported_driver | 검증 원문이 대상 기간 움직임과 사건을 명시적으로 연결 | 출처를 밝힌 보도상 배경. 유일한 원인으로 확정 금지 |
| relevant_event | 실제 회사 관련 사건과 시점은 확인, 가격 인과는 미확정 | 사건→사업 연결과 가능한 영향을 구분해 설명 |
| context_only | 회사 관련 사건 없이 시장/업종 자료만 있음 | 질문의 원인을 확인하지 못했다고 짧게, 관련 있는 비교만 선택 |
| unavailable | 검색/본문 실패 또는 유효 근거 없음 | 확보 범위·실패를 간결하게. 기사 부재라고 주장 금지 |
| conflicting | 중요한 사실에 충돌 | 공통 확인 사실과 충돌 지점, 결론 유보 |

구조: status, supportedClaims[{claimId,sourceIds,relation,timing}], missing[], conflicts[], retrievalOutcome.
retrievalOutcome은 no_results / domain_excluded / fetch_failed / timeout / date_rejected / entity_rejected / duplicate / insufficient_body 등 구분.
상태 판정은 구조·시점 검사를 코드로, 의미 연결은 제한된 추출 단계로 보완. 모델 분류만으로 causality 승격 금지.

## 7. 답변 프롬프트 생성 알고리즘
매번 자유롭게 프롬프트를 쓰는 에이전트 대신 버전이 있는 템플릿 조립기를 둔다.

prompt = 제품 공통원칙 + 의도별 목표 + 근거상태별 허용/금지 + 선택된 주장·원문근거 + 출력계약.
- 가격원인: 첫 문장에 질문에 대한 가장 강한 지원 가능 답 → 사건이 회사에 이어지는 과정 → 꼭 필요한 미확인점.
- relevant_event: '보도된 사실'과 '가능한 영향'을 분리. 기사를 찾았다고 가격 인과를 확정하지 않음.
- context_only/unavailable: 무관한 시장요약으로 분량 채우기 금지. 새 계약 등을 사용자에게 찾아보라고 떠넘기지 않음.
- 개념: 쉬운 정의/예시. 시장근거 부족 문구를 끼워 넣지 않음.
- 이어묻기: 기존 설명 반복 대신 새 궁금증에 집중. 신규 사실 필요할 때만 새 검색.
- 입력: 회사명, 기간, 질문 의도, 지원 가능한 주장, 근거문장/ID, 부족/충돌, 허용 추론범위. 제목-only 자료는 사실근거와 분리.
- 출력: currentStatus, keyAdvice(선택), assistantInsights(선택), followUps 및 내부 claimLinks. 내부 분류·점수는 사용자에게 노출하지 않음.
- UI는 회사명 중심. 사용자가 입력하지 않은 티커를 '질문에 적은'이라고 말하지 않음.

## 8. 생성 후 검증과 실패 처리
기존 수치·기간·근거 링크 검사에 다음을 추가한다.
1. 가격원인 질문에서 첫 부분이 실제 질문에 답하는가? 시장상황만 있고 회사 연결이 없으면 context_only 규칙 적용.
2. 계약/발표/실적/원인/날짜/숫자 주장마다 실제 근거가 있는가? sourceId 존재만으로 통과 금지.
3. relevant_event에서 확정 인과 표현, unavailable에서 임의 후보원인 나열 차단.
4. 추가 확인 과제가 특정 근거와 연결되지 않으면 keyAdvice 비움. '새 계약 확인해 보세요' 같은 일반 과제 제거.
5. 중요한 충돌·조건·불확실성이 생성 과정에서 사라지지 않았는가?

수정 생성은 최대1회, 전체 토큰/시간 예산에 포함. 실패 시 확인된 사실만으로 짧은 fallback. 자동 반복 생성 금지.
전체 응답을 매번 별도 대형 모델로 평가하지 않음. 규칙 검사 우선, 의미 검수 비용은 표본 평가에서 측정 후 결정.
중단 시 대기/생성 취소를 지원 가능한 범위로 전파. 공유 공개자료 작업은 다른 구독 요청이 있으면 개별 요청 취소로 끊지 않음. 실제 과금·이용횟수 정책은 별도이며 환불을 약속하지 않음.

## 9. 비용·캐시·관측
- 신규 구독 없이 기존 검색/provider 안에서 재배분부터 시작. 모델 교체는 비교평가 후 별도 판단.
- 공급자 API는 검색결과/본문 도구 어댑터로 분리. 현재 SDK 기능·정책은 구현 시 공식 문서로 검증.
- 조회예산을 실제 검색/fetch/토큰 단위로 추적. 의미추출 호출을 추가하면 총 비용에 포함, 공짜로 취급하지 않음.
- 캐시 키: 정규종목+기간+cutoff모드+정책버전. 원문은 canonical URL+수정시각, 사건은 사건ID. 답변보다 공개 근거 재사용 우선.
- 초기 기존5분 공개캐시 유지, 실패/부분 근거60초. 동시 동일조회 병합. 보완 단계는 이미 사용한 쿼리/원문을 반복하지 않음.
- 영구 저장/새 DB테이블 없이 시작, 크기·TTL 상한. DB IO 증가 측정 전 상시 뉴스수집 구축 금지.
- 관측은 원문·질문·계정 없는 집계: 단계시간, 호출수/비용, 후보수, 탈락사유, 근거상태, 수정횟수, fallback비율.
- 특정 사용자 원문 영구보관 안 함. 검수사례는 기존 명시동의 절차만 사용. 단계별 고카디널리티 개인로그 수집 금지.

## 10. 평가 및 구현 순서
평가셋: 공개·가상 질문 최소30개, 별도 보류셋10개. 시선AI 단일 사례에 맞춘 규칙 금지.
