# 개인 운영자를 위한 주비 개인정보 보호 준비

## 현재 판정

후속 업데이트: 2026-10-29 22:48 KST 기존 서비스 보안 패치·로그 보호를 운영 `dpl_DGLY9ZFRJazhUuwd9nQYfmfVCTsT`에 반영했다. 실제 투자 기록의 새 보관은 비활성이다. 최종 근거: [검증 보고서](../artifacts/portfolio-vault-20261029/REPORT.md).

**사용자 투자 기록을 운영자도 읽지 못하는 클라우드 보관은 아직 출시할 수 없다.** 암호화 기반 구현과 합성 검증은 시작했으나 실제 동기화·새 기기 복원·서버 알림·과거 평문 전환·독립 검토가 남아 있다. 현재 운영의 투자 기록은 기존 JSON 저장 방식이다.

사용자 요구: 탈취 예방과 유출 시 피해 제한을 함께 갖춘다. 개인 운영자가 사고를 감당하기 어려우므로 데이터 수집·보존 범위를 줄이고, 검증되지 않은 새 보관 방식이나 보안 약속을 먼저 공개하지 않는다. 사용자 기록을 임의로 삭제하거나 기존 동기화를 조용히 중단하지 않는다.

2026-10-30 후속 구현: 패스키 PRF·암호문 RPC·IndexedDB·연결 controller·DB 전환 제안을 격리 검증했다. 아래 표의 최초 기반 구현과 구분하며, [최신 전환 기준](PORTFOLIO_VAULT_ROLLOUT.md)을 따른다. 실제 제품 저장·운영 DB에는 아직 연결하지 않았다.

## 우선 처리할 공개 취약점

첫 `npm audit --omit=dev`는 설치/lock 기준 16개 취약 의존성(critical3/high8/moderate5)을 보고했다. 이는 패키지 판정이며 실제 악용 가능성이나 침해 사실을 뜻하지 않는다.

- Next.js 16.2.1은 여러 보안 공지의 영향 버전이다. 주비는 Node `next/og`를 사용하므로 ImageResponse 관련 공지는 우선 패치 대상으로 분류했다. 실제 공격 재현이나 침해 흔적 확인은 하지 않았다.
- Sentry tunnel 우회는 `tunnelRoute`·webpack·경로 충돌·middleware에만 의존하는 인증 등의 조건이 모두 필요하다. 현재 확인한 설정에 tunnelRoute가 없고 기본 Turbopack을 사용하므로 해당 조건이 확인되지는 않았다. 버전은 함께 패치한다.
- typed-array `use cache` RCE는 해당 함수를 쓰는 조건이 있다. 현재 소스에서 그런 사용을 찾지 못했다. 그래도 영향 버전 유지의 근거로 삼지 않는다.
- transitive MCP/Express 등은 개발 도구와 Google SDK의 optional peer 경로가 섞여 있다. 주비가 공개 MCP/Express 서버를 운영한다고 단정하지 않는다.
- 격리본에서 Next 16.4.3·동일 버전 ESLint config·Sentry 10.75.2 이상·Anthropic SDK 0.91.1 이상 및 호환되는 하위 의존성 패치를 준비한다. 최종 설치 버전·재감사·빌드 결과는 artifact로 기록한다.

최종 패치는 Next16.4.3/Sentry10.78.0/Anthropic0.91.1로 운영 반영했다. 운영 의존성 감사0건, 개발 도구까지는 낮음3건 잔여. 로컬 전체1,806tests/1skip 및 빌드, 원격1,803tests/4skip·빌드, 운영3화면 폭과 API/접근 차단 검수 통과. MFA 조회는 상태 필드가 없어 미확인으로 남겼고 실제 설정 상태를 사용자에게 질문했다. 사고 가능성0이나 독립 감사 완료라는 뜻은 아니다.

## 사고 대응 준비

아래는 **실행한 작업이 아닌 준비 순서**다. 실제 침해가 확인됐다는 뜻은 아니다.

1. 공개 보관 기능/쓰기/외부 전달을 어떤 경로로 중단할지 정하고, 실제 권한·정상 복구 절차를 격리 환경에서 검증한다. 검증되지 않은 SQL/전면 pause를 운영에 즉시 적용하지 않는다.
2. 사고 시각·영향 서비스·토큰/권한 범위를 기록하고 원본 증거를 보존한다. 로그/행을 일괄 삭제해 원인을 없애지 않는다.
3. 침해 범위에 맞게 세션·API 비밀·운영 계정 권한을 회수/교체한다. 모든 설정을 무작정 교체해 정상 접근과 증거 보존을 잃지 않도록 절차를 마련한다.
4. 개인정보 유출 판단, 사용자 통지·기관 신고의 해당 요건과 시기를 확인할 연락·검토 경로를 준비한다. 암호화했다는 이유만으로 통지/신고나 책임이 없어졌다고 단정하지 않는다.
5. 새 키/수정 코드로 별도 검증 후 서비스를 복원하고 재발 방지 결과를 확인한다. 단순 재배포를 사고 해결로 보지 않는다.

## 사용자 안내 기준

- 현재 안내: 계정별 서버 저장이며 운영자도 읽을 수 없는 암호화는 아직 적용 전이라는 사실을 유지한다.
- 전환 후 안내: 보호한 투자 기록의 범위, 서버의 키 보유 여부, 새 기기/분실 복원, 외부 공유 예외를 구체적으로 설명한다.
- ‘유출되어도 모든 데이터가 무의미’, ‘100% 안전’, ‘개인정보가 전혀 없음’, ‘운영자도 어떤 상황에서도 읽을 수 없음’은 사용하지 않는다.
