# 회사 설명 전체 확장·자동 운영 준비

작성 2026-11-02 KST. 실제 운영 자동화 확대는 장애 복구와 출시 조건 확인 후 진행한다. 현재 관찰만으로 전체 해결 또는 완전 자동화 준비 완료라고 선언하지 않는다.

## 구현된 실행 경로

공개 화면 검사 → 누락 작업 → 식별자/지문 manifest → 기존 수집 큐 → 하루 제한 내 수집·초안·검수 → 편집 승인 대기 → 공개 진행 조회 → 같은 버전의 실제 화면 확인.

`quality-lab/src/automation.mjs`는 순서를 실행하는 독립 코어, `scripts/run-quality-improvement.mjs`는 서비스 자격 증명이 있는 별도 운영 환경의 어댑터다. 공개 작업실 서버는 운영 DB/회원정보를 알지 못한다. 현재 영구 호스팅/자동 스케줄링 배포는 안 했다.

- 기본 관찰 모드, 실행은 명시적 플래그와 건강/할당량 조건이 모두 필요.
- 상태·SQL 경로·디스크 계측 누락/노후/실패 시 운영 쓰기/생성 시작 안 함. 장치별 read/write/bytes가 모두 있어야 하며, 같은 값의 캐시 표본은 낮은 부하 증거로 통과시키지 않음.
- 실제 worker는 격리된 검증 릴리스의 src·실행 스크립트·패키지 manifest SHA-256에 결속. 변경 중인 원본 workspace를 실행 대상으로 삼지 않으며, 지문이 바뀌면 멈춤. 인증정보/환경파일은 지문이나 작업실로 옮기지 않음.
- 같은 통계 기간 1~15분 차이에서 장치별 합산 IOPS 50 이하/throughput 1 MiB/s 이하를 보수적 파일럿 조건으로 사용. 디스크/파티션을 합쳐 중복 계산하지 않음. 이는 실제 Disk IO 잔여 예산 판정이 아니다.
- 장애 보류는 건강한 표본 하나로 자동 해제되지 않음. 회복·부하 원인·재개 범위를 확인한 뒤 정책을 변경.
- 현행 상한 내 최대 1~3회, 실행 전에 일일 시도를 기록. 타임아웃/재시작 때문에 같은 시도가 무제한 반복되지 않음. 작업 사이에도 실제 DB 경로 확인, 실패/보류/빈 큐면 중단.
- 동일 manifest 전달은 한 번, 수집 화면은 하루 한 번 이하. DB의 기존 작업/모델 예산과 별도 중복 방어이며 그 예산을 늘리거나 리셋하지 않음.
- 새로운 편집 승인·공개·배포 권한은 주지 않음. 이미 승인된 내용과 근거가 그대로인 갱신만 기존 정책으로 재사용.

## 처리량의 실제 한계

기존 목록 8,020개, 검증된 엔진 공개본 1개. 하루1회/한 번1작업이면 남은 8,019개에 최소8,019일(약22년)이 걸린다. 하루3건을 전부 처리해도 최소2,673일이다. 재수집·재시도·검수 대기까지 제외한 하한이므로 일정 약속이 아니다. 이 설정은 파일럿용이다.

전체 확장 준비는 다음 순서로 한다.

1. 발행사 목록/분류 충돌과 원천 미지원 정리. SEC 목록 일치5,277은 설명완료 숫자가 아니다. 국내2,683은 인증 연결 후 실제 공시 확인.
2. 원문 수집과 모델 작성을 분리. 목록·문서는 조건부 HTTP와 지문으로 변경 여부를 확인하고, 바뀐 문단만 처리. 원문/화면/실패 증거를 회원 DB에 누적하지 않음.
3. 이미 검수된 설명은 회사·근거·정책이 일치하고 유효기간 내일 때 재사용. 이번 후보는 변하지 않은 설명의 갱신을 2회 체크포인트에서 1회로 줄인다. 물리 I/O 절감률은 실측 전.
4. 초기 전체 채움과 정기 갱신을 별도 용량으로 계획. 실제 Gemini 무료 한도와 한 작업의 토큰/검수 비용을 확인해 하루 완성 가능한 설명 수를 산정. 내부달러가드가 실제 청구액은 아님.
5. 초보자에게 실제 도움이 되는 답의 기준으로 검수 범위를 확장. 보류만 늘리는 평가기도 정상 제공률과 함께 평가.
6. 월간/분기 공시와 정정을 따라가는 지속 갱신. 모든 회사 last_seen 매일 갱신을 재도입하지 않음.

## 자동 공개를 여는 조건

CARG 초안2개를 모델 검수가 잘못 통과시킨 실사례가 있다. 따라서 검수 모델과 생성 모델을 단순히 두 번 부르는 것으로 독립 검증 완료를 주장하지 않는다.

- 검증된 수치/정형 사실 템플릿, 변경 없는 승인 설명 재결속, 새 회사 설명, 사건 해석/주가 원인 서술을 서로 다른 공개 범위로 관리.
- 고정 정답 사례와 미사용 holdout, 국가/규모/산업/자료부족/정정·실패를 포함한 실제 사례, 모델과 독립된 원문 판단이 필요.
- 기존 시장원인 평가지표의 200사건·10거래일은 실제 자료여야 하며 합성자료/개발10종목으로 대체하지 않음. 회사 설명도 별도 대표성/오판률/검토자 일치도를 측정.
- 중대한 근거 없는 공개가 있으면 해당 유형 보류. 높은 디자인 점수로 사실 오류를 상쇄하지 않음.
- 유형별 허용 정책과 만료/철회·오류 복구 시간을 검증한 후 자동 공개를 순차적으로 허용. 스케줄러 배포 자체는 의미 정확성의 증거가 아님.

## 복구와 재개 절차

1. Supabase Database Health에서 11/1 07:40 UTC 경고 전후 CPU/메모리/스왑/읽기·쓰기 IOPS/잔여 budget과 예약 작업을 대조. 현재 대시보드 로그인 필요. API의 ACTIVE_HEALTHY만으로 DB가 실제 정상이라고 판단하지 않음.
2. 연결 회복 직후 `capture-io-snapshot.mjs`로 새 baseline 저장. 장애 시각의 실패 표본과 차이를 계산하지 않는다. 1~15분 후 같은 통계 epoch의 두 번째 표본으로 차이를 확인.
3. 공개·회사·시장 전용 스키마의 갱신과 WAL/디스크/메모리를 비교. 사용자 행·SQL 원문·토큰은 기록하지 않음. 통계 리셋/대량VACUUM/재색인 금지.
4. 현재 장애의 원인이 잔여 I/O 고갈이면 재시작이 예산을 되돌리지 않는다. 공식 안내는 예산 회복 대기 또는 compute확대다. 실행 중 부하/원인 모르는 반복 재시작을 자동화하지 않는다.
5. 1건 canary → 실제 원문/판정/쓰기량/화면 전달 → 제한된 순환 표본 → 처리량 확대. 건강 표본 하나로 전체8,020개를 실행하지 않는다.
6. 운영 변경은 이전 검증 정본에서 선택 파일만 반영. 루트 전체 배포 금지. 이번 앱 후보는 `/private/tmp/joobi-automation-preparation-20261101`(회사 갱신2파일), 현재 운영은 이전 Adg배포다.

공식 근거: [I/O 경고](https://supabase.com/kb/troubleshooting/exhaust-disk-io), [HTTP 장애와 재시작 한계](https://supabase.com/kb/troubleshooting/http-api-issues), [프로젝트 장애 점검](https://supabase.com/kb/troubleshooting/failed-to-retrieve-tables). 변경 가능한 컴퓨트 사양은 [공식표](https://supabase.com/docs/guides/platform/compute-and-disk)를 재확인한다.
