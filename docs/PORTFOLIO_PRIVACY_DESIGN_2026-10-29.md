# 투자 기록을 운영자도 읽을 수 없게 만드는 설계

상태: **설계 초안·암호화 기반 일부 구현. 실제 투자 기록 암호화 보관은 운영 미적용.**

2026-10-30: 패스키 PRF·암호문 RPC·IndexedDB·연결 controller와 DB 전환 제안까지 격리 구현했다. 홈의 비활성 보호 분기에 읽기 전용 잠금 화면을 연결했고, 재개 가능한 전환 coordinator와 개인 알림 중단 경계를 추가했다. 기존 데이터 이관 UI·편집/설정·운영 전환은 미완료다. 최신 구현과 남은 전환 조건은 [전환 기준](PORTFOLIO_VAULT_ROLLOUT.md)을 따른다.

2026-10-29 후속: 기반 crypto/payload·합성 검증을 추가했고 기존 서비스의 의존성 보안 패치·오류 수집 보호·IP 보존 누락 수정은 운영 반영했다. 현재 동기화는 여전히 JSON 저장이다. 완료 범위와 미해결 조건은 [검증 보고서](../artifacts/portfolio-vault-20261029/REPORT.md), [출시 준비 기준](SECURITY_READINESS_2026-10-29.md)을 따른다.

사용자 요구: 투자 기록의 내용을 운영자·개발자가 알 수 없어야 하며, 저장 서버의 정보가 유출돼도 그 정보만으로 해독할 수 없어야 한다. 안내보다 실제 구조와 검증이 먼저다.

후속 요구를 두 단계로 적용한다.

1. **탈취 예방**: 불필요한 개인정보 수집·보존 최소화, 인증·계정 격리·최소 권한·비밀 관리·접속 감시.
2. **유출 시 피해 제한**: 사용자만 가진 키로 투자 본문을 보호하고, DB/서버 설정만으로 해독할 수 없게 한다. 알림·문의·로그·백업의 우회 노출까지 점검한 뒤 사용자에게 검증된 범위를 알린다.

이름을 삭제하거나 계정 ID로 바꾸는 것만으로 익명 정보가 되는 것은 아니다. 다른 정보와 쉽게 결합해 사람을 알아볼 수 있는 정보와 가명정보도 개인정보에 해당한다. 로그인 식별자·연락처와 연결된 투자 기록에 대해 ‘개인을 식별하지 않으므로 유출돼도 문제가 없다’고 판단하거나 홍보하지 않는다. 아래의 암호화도 모든 정보를 익명화하는 처리는 아니다.

## 조사 기준과 현재 상태

- 기준: 2026-10-29 운영 소스 `dpl_FXV7cbymGqvegruTVG5Kp4yzUUQ2`. 복원한 운영 소스에서 아래 경로를 읽었다. 사용자 투자 내용이나 인증 정보를 조회·수집하지 않았다.
- `src/lib/portfolioSync.ts`: `user_portfolios.stocks`, `daily_snapshots`, `portfolio_history`를 JSON으로 읽고 쓴다. 클라이언트 암호화가 없어 DB 운영 권한으로 투자 내용을 읽을 수 있다.
- `src/hooks/usePortfolioSync.ts`: 로그인 후 자동으로 클라우드 기록을 읽고 변경을 동기화한다. 일상적인 기기 이동에 파일 내려받기·가져오기를 필수로 요구할 이유는 없다.
- RLS와 인증된 사용자 ID 검사, CAS는 계정 격리와 덮어쓰기 방지에 필요하다. 운영자나 탈취된 관리자 권한이 내용을 읽지 못하게 하는 장치는 아니다.

## 목표와 한계

- DB 덤프, 서비스 권한, 서버 환경변수, 서버 측 백업만 가진 공격자가 기존에 암호화된 투자 본문을 해독할 수 없게 한다. 주비도 사용자 복호화 키를 갖지 않는다.
- 사용자는 자신의 기기·복구 수단으로 정상 복원할 수 있어야 한다. 데이터를 해시하거나 모두 파기하는 방식은 이 요구를 충족하지 않는다.
- 기기·브라우저 확장·잠금 해제된 세션의 탈취, XSS, 악의적으로 바뀐 웹 코드가 평문/키를 읽는 공격은 별도 대응이 필요하다. 웹 앱을 배포하는 운영자를 어떤 상황에서도 신뢰할 필요가 없다는 절대 보장은 할 수 없다.
- 암호화는 서버의 데이터 삭제·서비스 거부·과거 암호문 재전송을 자동으로 막지 않는다. 무결성·신선도·복구 가능성도 따로 검증한다.
- ‘어떤 해킹에도 안전’, ‘모든 개인정보를 알 수 없음’, ‘절대 복구 불가능’은 사용하지 않는다.

## 암호화·키 관리 요구

1. 기기에서 암호학적 난수로 계정별 데이터 키를 생성한다. 검증된 API/라이브러리의 인증 암호화(예: AES-256-GCM)를 사용하며 자체 암호 알고리즘·프로토콜을 만들지 않는다.
2. nonce 재사용을 방지하고 형식 버전·계정·기록 종류를 인증 데이터에 묶는다. 잘못된 키·손상·다른 계정 암호문은 오류로 처리한다. 복호화 오류를 ‘빈 포트폴리오’로 간주해 저장하지 않는다.
3. 서버는 암호문·필요한 버전/동기화 메타데이터와 사용자 비밀 없이는 풀 수 없는 키 포장본만 보관한다. 환경변수나 운영자용 마스터키로 복호화하는 우회 경로를 두지 않는다.
4. 사용자 ID·이메일·카카오 토큰처럼 서버가 알 수 있는 값으로 복호화 키를 만들지 않는다. 일반 카카오 OAuth 인증 성공 자체를 암호화 비밀로 취급하지 않는다.
5. 새 기기 복원에는 사용자만 가진 복구 수단 또는 기존 기기의 안전한 승인이 필요하다. 짧은 PIN만으로 서버 탈취 후 오프라인 추측 공격에 대응했다고 판단하지 않는다. 복구 코드의 엔트로피, 암호 사용 시 KDF와 기기 성능을 검증한다.
6. 기존 기기 승인은 서버의 공개키 바꿔치기를 고려해야 한다. 검증된 프로토콜·별도 확인 없는 단순 QR/키 전달을 안전하다고 간주하지 않는다.
7. 키 교체·기기 분실·로그아웃·저장소 삭제·계정 전환·두 기기 충돌·옛 클라이언트를 함께 설계한다. 복구 수단을 모두 잃으면 운영자가 복호화해 돌려줄 수 없다는 점을 설정 시 알린다.

## 기존 데이터 전환

- 사용자 기기에서 기존 기록을 읽고 암호화해 별도 버전으로 저장한 뒤 동일·새 기기 복원을 검증한다. CAS·충돌 처리와 되돌림 정책을 유지한다.
- 암호화 저장 성공만 보고 평문을 즉시 지워 데이터 손실을 만들지 않는다. 사용자별 전환 완료와 보존/삭제 절차 확인 뒤 기존 쓰기 경로와 평문 컬럼을 닫는다.
- 이전 DB 백업, WAL/PITR, 발송 대기열·이력, 로그와 외부 수탁 사본은 별도 확인한다. 즉시 소거할 수 없는 사본은 잔존 기간을 알린다.
- 앞으로 암호화해도 이미 유출된 평문을 보호하거나 회수할 수는 없다. 이번 조사에서 실제 유출을 확인한 것은 아니다.

검증 후 안내 초안:

> 투자 기록은 기기에서 암호화한 뒤 보관합니다. 주비 서버에는 기록을 여는 키가 없어, 저장된 암호문만으로는 내용을 읽을 수 없습니다. 새 기기에서는 복구 수단이 필요하며, 이를 모두 잃으면 주비도 복원해 드릴 수 없습니다.

이 문구는 **현재 운영 화면에 적용하지 않는다.** 로그인 식별 정보·접속 기록과 사용자가 선택한 외부 공유 범위는 따로 안내해야 한다.

## 미결정 사항

- 새 기기에서 1회 복구 암호/기존 기기 승인이라는 추가 단계 허용 여부를 사용자에게 질문했고 답변 대기 중이다. 카카오 로그인만으로 모든 새 기기에서 풀어 주겠다고 약속하지 않는다.
- 기기를 켜 두지 않아도 받던 맞춤 알림의 대안은 요구사항 확정 뒤 실제 기기·백그라운드 실행 제약을 검증해야 한다. 이번 조사로 알림을 끄거나 저장 구조를 변경하지 않았다.

## 토스 비교와 로그인 복원 요구

사용자는 ‘계정 로그인으로 바로 연결되는 것이 자연스럽다’고 지적하고 토스의 방식을 질문했다. 앞서 복구 키를 설명한 것은 **서비스도 키를 갖지 않는 엄격한 보호 모델**을 전제로 했으며, 모든 서비스에서 수동 복구 키가 필수라는 뜻이 아니다. 사용자 요구를 바꿨다고 해석하지 않는다.

- 토스의 공개 보안 안내는 휴대전화 교체/재설치 후 이용 편의를 위한 로그인 정보의 암호화 서버 저장을 설명한다.
- 토스의 2025-12-12 제7차 데이터보호 준법 자문위원회 자료는 중앙 KMS에서 키 생성·저장·폐기를 관리하고 HSM을 활용한다고 설명한다. 직원 권한 세분화와 로그 통제도 공개한다.
- 이것만으로 모든 토스 서비스·투자 정보의 내부 키 경로나 직원별 열람 가능 여부를 단정할 수 없다. 특히 ‘토스도 회사가 절대 복호화할 수 없는 E2EE’라고 해석하지 않는다.

| 주비의 선택 가능한 방향 | 로그인·복원 | 보호 범위와 제약 |
| --- | --- | --- |
| 서비스가 엄격한 권한 아래 키를 관리 | 본인 인증 후 서비스가 복호화해 자동 제공 가능 | 별도 키 관리·접근 통제·감사 필요. DB만 탈취된 경우와 서비스의 복호화 권한까지 탈취된 경우를 구분해야 함. ‘주비도 복호화할 수 없다’는 기존 요구와는 다름 |
| 사용자만 키를 갖는 보호 유지 | 같은 기기는 자동 처리 가능. 새 기기는 사용자 측 키를 옮기거나 복구해야 함 | 손으로 복구 코드를 입력하는 방법만 있는 것은 아님. 기존 기기 승인·기기/플랫폼 키 동기화 등의 가능성을 호환성·분실 복구·제3자 신뢰 범위까지 검증해야 함. 현재 카카오 OAuth만으로 이 비밀을 얻을 수 있는 것은 아님 |

로그인만으로 복원하는 편의를 위해 서버에 키를 두는 방향을 임의로 채택하지 않는다. 기존의 ‘운영자도 내용을 알 수 없음’ 요구를 유지할지, 서비스의 제한적 복호화를 허용할지 먼저 정해야 한다. 사용자에게 손으로 관리하는 복구 키를 무조건 요구하는 UX도 아직 확정하지 않았다.
