# 주비 지속 개선 순환 설계

2026-11-01. 사용자 요청: 평가 엔진을 지속적으로 개선하고, 개선된 데이터를 주비까지 전달하는 사이클을 설계한다. 아래는 전체 설계와 첫 개발용 연결의 구현 상태다. 운영 공개 정책은 변경하지 않았다.

## 목적과 현재 위치

### 2026-11-03 후속 — 기업 내용과 화면 설명을 한 종목에서 검수

사용자는 기업 설명과 화면 설명을 모두 개선해야 한다고 재확인했다. 작업실0.6.0은 기존 기업 설명의 화면 본문(사업·고객·수익·점검)과 출처를 수집하고, 누락·반복·긴/추상 문장을 편집 과제로 남긴다. 같은 종목의 설명 탐색·용어 창·후속 질문 관측과 함께 상태를 표시한다. API에 일부 항목이 없더라도 정적 화면에서 제공되는 내용을 먼저 읽으므로 표시 계층의 차이를 누락으로 오탐하지 않는다.

이미 제공 중인 설명의 문제는 `company-content-review`로 분류한다. 원문을 보고 실제 문장을 수정할 과제이며, 자동 재생성 요청에 조용히 섞지 않는다. 기존 회사 설명 전달 완료도 공개 버전·후속 운영 수집·표시 본문 관측·알려진 기업 내용 결함 부재가 필요하다. 화면 전달 확인과 사실의 의미/초보자 이해도 검수를 구분한다.

기계 검사 통과는 원문과 해석의 정확성을 보증하지 않는다. 콘텐츠와 전달 두 영역의 상태가 관측돼도 별도 의미 검수는 남는다. 실제 콘텐츠 정정·원문 대조 자동화·상시 실행은 아래 기존 운영 조건을 유지한다. 이번에는 모델/DB/운영 앱을 변경하지 않았으며 과거10표본의 규칙 재평가와 로컬66검사를 수행했다.

개인 주식비서가 중요한 변화를 챙기고, 정확한 근거로 회사·사건·의미·내 투자와의 관계를 설명하도록 한다. 틀린 내용, 회사 이름만 바꾼 반복 문장, 답이 없는 질문은 핵심 제품 결함이다. 평가 점수 상승보다 확인된 결함 감소와 유용한 설명 범위 확대를 우선한다.

현재 구현된 것은 `quality-lab/`의 화면 수집·패턴 탐지·근거 기록·채점 검증·전후 비교와 기업 설명 엔진의 출처/초안/검수/편집승인/공개 읽기 구조다. 추가로 ALLR 공시→근거가 연결된 후보→개발용 API→질문/답 화면의 첫 연결을 구현했다. 원문 의미 검증의 자동화, 후보 자동 작성, 운영 게시 연결, 코드 개선 생성, 상시 실행은 아직 미구현이다. 초기10개는 개발에 사용한 기준 사례이며 독립 검증 표본이 아니다.

### 첫 연결의 실제 범위

- 공통 라우팅: ‘계약’만으로 수주 개념을 연결하던 규칙에서 주식 거래·대출·라이선스 등 계약 종류와 종료/추진 단계를 제외. 서로 다른 기사의 태그를 독립적으로 합친다.
- 일반 학습: 근거가 없을 때 첫 실적 질문을 강제로 고르는 동작과 회사 맞춤처럼 보이는 제목을 제거. 관련 개념·일반 자료실로 구분한다.
- 후보 자료: SEC 8-K `000121390026114380`의 ALLR/Tumim 신주 매각 계약 종료를 사례로 사용. 구조화 초안은 작성자가 제공하며 컴파일러0.1.0이 출처 내 위치/식별/날짜/무결성을 검사. 의미 검수 대기 상태 유지.
- 전달: 불변 후보 저장→검토 UI→명시적 `export-preview`→개발용 `/api/stock-context`→선택 종목/사건 기사와 일치하면 표시. DB 쓰기나 모델 호출 없음. 운영에서는 후보 응답을 차단한다.
- 검증: [이번 검사 보고서](../artifacts/quality-cycle-20261101/REPORT.md). 일반 규칙과 UI 변경도 현재는 격리 로컬 후보이며 운영 반영 전이다.

## 서로 연결하되 분리하는 두 순환

### A. 주비 콘텐츠와 경험을 개선하는 순환

운영 화면·공식자료 변경·사용자 문제 제보 → 증거 수집 → 결함 분류 → 개선 후보 → 검증 → 공개 버전 전환 → 실제 운영 재검사 → 새 결함/학습 사례.

### B. 평가 엔진을 개선하는 순환

놓친 결함·오탐·평가자 불일치 → 원문 대조와 정정 → 재현 사례 → 평가 규칙/판정 프롬프트/모델 후보 → 기존·신규 검증 자료 비교 → 평가 버전 전환 → 다음 운영 평가.

평가기가 자기 점수를 근거로 자기 변경을 승인하지 않는다. 새 평가기는 기존 평가기와 같은 고정 입력을 판정하고, 실제 대조한 정답 사례에서 누락·오탐을 비교한다. 프롬프트 개선은 모델 학습과 구분하며, 파인튜닝을 도입한 것으로 표현하지 않는다.

## 1. 관찰과 증거 고정

- 고정 오류 사례: ALLR의 주식 매입 계약 종료→수주/납품 연결, 회사 소개 없이 맞춤 질문 노출, 반복되는 실적 질문 등.
- 순환 표본: 국가·산업·기업 규모·설명 제공 수준·기사 유무·사건 종류를 나눠 선정. 유명 기업이나 이미 잘 되는 종목만 검사하지 않는다. 일일 표본 수는 자원 상한 내에서 설정한다.
- 변경 우선 표본: 새 공시/정정/회사 변경, 새 공개 버전, 실제 문제 제보가 있는 종목. 사용량을 쓴다면 개인정보 없는 집계만 사용한다.
- 수집 시 회사 식별자, 화면/API/공시 문단, 기준 시각, 출처와 콘텐츠 지문, 수집기 버전, 브라우저·화면 크기를 고정한다.
- 같은 소식을 여러 매체가 전한 경우 사건 단위로 묶는다. 출처 수나 제목 다양성을 독립 증거 수로 세지 않는다.
- 실패 표본을 다른 종목으로 바꾸지 않는다. 검사 도구 자체의 오류는 재현 후 무효 기록으로 남겨 제품 결함/개선 점수에서 제외한다.

## 2. 원인에 맞는 개선 경로

| 발견한 문제 | 처리 경로 | 주비에 전달할 결과 |
|---|---|---|
| 회사 설명 없음·빈약함 | 발행사 식별 → 공식 자료 확보 → 사업/고객/수익 구조 작성 | 검증된 회사 설명 |
| 기사와 해설의 문맥 충돌 | 사건 종류·당사자·단계·기간 구조화 → 연결 규칙 수정 | 사건 해설 및 질문/답 연결 |
| 근거 없는 주장·수치 혼용 | 원문 대조 → 정정 또는 해당 주장 제외 → 누락 자료 수집 | 수정된 주장과 근거 |
| 이름만 바꾼 일반 질문 | 답할 근거와 왜 이 질문인지 검토 → 질문/답 쌍 구성 | 근거가 있는 다음 질문 |
| 읽기 위계·탐색·모바일 문제 | UI 변경 후보 → 동일 데이터로 화면 비교 | 코드 변경과 배포 |
| 검사 오탐·누락 | 판정 기준 정정 → 재현 사례 → 평가 버전 검증 | 새 평가 엔진 버전 |

일반 개념은 별도 자료로 유지할 수 있다. 같은 개념이 여러 종목에 등장하는 것 자체를 오류로 단정하지 않는다. 해당 회사·기사의 맞춤 분석처럼 표시하거나 질문의 약속과 실제 답이 다를 때 결함으로 판단한다. 새로운 질문을 무작위로 돌려 반복률만 낮추지 않는다.

## 3. 개선 데이터의 계약

주비가 받을 것은 평가 로그나 자유 형식의 긴 AI 응답이 아니라 검증된 설명 묶음이다. 내용과 전달 경로를 함께 관리한다.

| 영역 | 필수 내용 |
|---|---|
| 식별 | symbol, 안정적인 발행사ID, 시장, 언어, 상품 종류 |
| 시점 | 사건 발생/발표 시각, 자료 기준 기간, 확인일, 재확인 기한 |
| 사건 | 종류(예: 자금 조달/판매 계약), 단계(신청/체결/종료 등), 당사자 |
| 설명 | 한 줄 요약, 확인된 사실, 그 의미, 전달 과정, 모르는 부분 |
| 주장과 근거 | claim ID, 원문 문단/구절 ID, 출처 URL·문서ID·지문, 사실/해석/가상 예시 구분 |
| 다음 탐색 | 질문, 지금 이 질문인 이유, 실제 답, 답의 근거, 관련 설명·복귀 경로 |
| 변경 이력 | contentVersion, sourceHash, generatorVersion, evaluatorVersion, rubricVersion, 검수 기록 |
| 공개 제어 | schemaVersion, release ID, validUntil, 철회 상태, 이전 유효 버전 |

공개 화면에는 사용자가 이해에 필요한 출처·시점·자료 범위만 보여준다. 내부 평가 점수·모델 프롬프트·운영 상태를 제품 본문에 나열하지 않는다. 구조화된 텍스트와 제한된 UI 블록만 전달하며 임의 HTML/스크립트를 실행하지 않는다.

회사 소개와 당일 사건 해설은 갱신 정책을 다르게 둔다. 연차보고서 기반 회사 소개의 유효기간을 당일 뉴스 해설에 그대로 적용하지 않는다. 예상/확정/정정도 구분한다.

## 4. 후보 검증

1. **기계 검사:** 회사·기간·통화·단위·출처 결속·정정/철회·필수 답변·수치 계산·질문 목적지·캐시 상태를 확인한다.
2. **의미 대조:** 생성과 분리된 검수에서 문장 전체가 원문으로 뒷받침되는지, 조건부/미래 사건을 확정 사실로 바꿨는지 확인한다. 같은 모델을 다른 프롬프트로 호출하는 것만으로 독립성을 확보했다고 하지 않는다.
3. **초보자 경험:** 회사→사건→의미→다음 질문 흐름, 용어 풀이, 실제 답의 정보량, 반복, 읽기 위계, 모바일/키보드/다크 상태를 본다.
4. **회귀 검사:** 알려진 오류와 정상 사례 양쪽을 확인한다. 사건 표현이 조금 바뀐 사례, 계약 체결과 종료, 수주와 자금 조달을 포함한다. 개발자가 본 자료와 미사용 검증 자료를 구분한다.
5. **효과 판단:** 동일 자료를 고정한 전후 비교로 코드·설명 개선 효과를 확인한다. 실시간 운영 재검사는 별도로 수행해 새 뉴스 유입 효과와 섞지 않는다.

검사에서 발견된 치명적 오류 또는 필수 근거 미확인은 공개를 막는다. 총점은 우선순위와 경향을 보는 보조 값이며 단일 ‘80점 이상 자동 공개’ 규칙은 사용하지 않는다. 검사를 통과한 결과도 무오류 보장은 아니다.

## 5. 주비로 전달하는 경계

구성: **개선 작업실/worker → 비공개 후보 저장소 → 공개 담당 모듈 → 버전이 고정된 공개 설명 저장소 → 주비 API·CDN → 화면**.

- 개선 worker는 사용자 DB 접근·운영 코드 직접 배포 권한을 갖지 않는다. 공개 담당 모듈만 검증된 manifest를 받아 허용된 설명 영역을 갱신한다. 공개 권한과 검수 권한을 분리한다.
- 후보와 공개본은 불변 버전으로 저장한다. 동일 출처·후보 지문의 중복 작업을 합친다. 공개 전환은 예상 이전 버전을 확인한 원자적 포인터 전환으로 처리한다. 늦게 끝난 작업이 새 설명을 덮어쓰지 않게 한다.
- 기존 **회사 설명**은 `BusinessPublicProfile`과 `/api/company-profile`을 재사용한다. `readPublishedBusiness`의 출처·초안·편집승인 결속과 철회/만료 검사를 우회하지 않는다.
- **뉴스별 사건 해설/질문**은 새 저장 계약과 공개 조회 경로가 필요하다. `StockReturnBrief`와 `StockLearning`이 검증된 연결을 읽도록 변경한다. 기존 제목 키워드→일반 질문 선택을 그대로 두고 설명 DB만 채우는 것으로 완료하지 않는다.
- **디자인·연결 코드 수정**은 코드 변경→후보 배포→화면 검사→운영 배포 경로를 쓴다. 데이터 수정과 코드 배포를 분리해 이력을 남긴다.
- 정상적인 새 후보가 검수 대기일 때 기존 공개본이 여전히 유효하면 유지한다. 출처 정정·오류·철회·만료가 발견되면 해당 주장/내용을 먼저 보류한다. 과거의 철회된 설명을 기본값으로 되살리지 않는다.
- 철회 시 공개 포인터뿐 아니라 해당 API/CDN/앱 캐시를 무효화한다. 공개 read에는 만료/철회 경계를 유지하며 전달 장애를 정상 응답으로 캐시하지 않는다. 반영 완료는 운영에서 같은 버전이 실제 보이는지 재검사한 뒤 기록한다.

## 6. 자동화 수준과 운영 제어

초기에는 기존 편집승인 정책을 유지한다. 점수 상승이나 모델 검수만으로 `editorial` 기록을 자동 생성하지 않는다. 개선 작업마다 사용자에게 다시 허락을 요청한다는 뜻이 아니라, 공개를 담당하는 제한된 운영 절차가 실제 근거 대조를 기록해야 한다는 뜻이다.

검증된 범위가 쌓이면 사건 유형별로 자동 공개 허용을 확대한다. 첫 후보는 검증된 수치를 고정 템플릿으로 설명하거나 이미 승인된 설명에 최신 출처를 결속하는 범위다. 의미가 바뀌는 회사 설명·주가 원인 서술·복잡한 계약 해석은 별도 실평가를 거친다. 별도 승인 정책 변경과 버전 기록 없이 기존 보호 장치를 끄지 않는다.

출시 단위는 사용자별로 검증되지 않은 사실을 시험하는 것이 아니라 검증을 마친 종목/사건 유형의 범위를 작게 넓히는 방식이다. 사용자 실험은 사실 정확성을 먼저 통과한 표현·배치·탐색 후보에서만 한다.

오류 발생 시 해당 release를 중지하고 이전의 **아직 유효한** 공개본으로 되돌린다. 이전본도 무효라면 확인된 사실과 출처만 남기고 잘못된 해설을 숨긴다. 실패한 작업은 재시도 횟수/대기 시간을 제한하고 중단·재개·실패 큐를 제공한다.

## 7. 평가 엔진의 지속 업데이트
