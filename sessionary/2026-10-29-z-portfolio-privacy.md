# 2026-10-29 - 클라우드 투자 기록의 운영자 비공개 요구

## 작업 요약
- 로그인 배포 도중 사용자가 클라우드 보관·수동 파일 이동 필요성과 서버 유출 시 보호를 질문했고, ‘운영자도 사용자 투자 정보를 알 수 없어야 한다’고 정정했다.
- 자동 동기화 코드와 운영 소스를 읽어 현행 JSON 저장·서버 알림 의존을 확인했다. 사용자 투자 내용이나 비밀정보는 조회하지 않았다.
- 실제 구조가 바뀌기 전 ‘우리는 못 읽는다’고 안내할 수 없음을 설명했다. 요구·보호 범위·현행 흐름·전환·검사 기준은 `docs/PORTFOLIO_PRIVACY_DESIGN_2026-10-29.md`에 정리했다.
- 새 기기 1회 복구 수단/기존 기기 승인 허용 여부를 비동기 질문했다. 아직 답변이 없어 키 복구에 의존하는 구현은 진행하지 않았다.
- 앞서 승인된 로그인 변경은 운영 반영·검수 완료. 최종 보고서 `artifacts/login-release-20261029/REPORT.md`. 개인정보 보호 구조 변경은 포함하지 않았다.
- 후속 질문에서 탈취 예방과 유출 시 해독/악용 방지 두 기준을 재확인했다. 개인정보 최소화·식별자 연결·발송 대기열·문의 webhook의 잔존 위험을 설계 문서에 추가했다. 단순 이름 제거를 익명화/무위험으로 보지 않는 근거로 현행 법 제2조와 개인정보위 안내를 확인했다. 사용자 실제 값이나 운영 webhook 설정은 조회하지 않았다.
- 사용자가 복구 키의 불편과 로그인 자동 연결을 지적하며 토스를 질문했다. 토스 공식 보안·보호 원칙·2025-12-12 자문위 자료의 중앙 KMS/HSM과 권한 통제를 확인했다. 수동 복구 키가 모든 서비스의 필수 조건이라는 오해를 바로잡고, 서비스 관리 키와 사용자 관리 키의 보장 차이를 설계 문서에 추가했다. 기존 비가독성 요구를 철회한 것으로 해석하거나 서버 관리 키로 조용히 전환하지 않았다.

## 결정사항
- 요구와 구현 상태를 구분하고 먼저 운영 데이터 흐름을 조사했다. 평문 저장을 유지하면서 ‘운영자도 읽을 수 없다’는 문구만 추가하지 않는다.
- 보유 기록만 암호화해도 서버 알림·발송 이력·백업으로 우회 노출될 수 있어 이 경로까지 설계 범위에 넣었다. 편의나 알림을 임의로 중단하지 않았다.
- 주비가 사용자 기록을 복구할 수 있게 마스터키를 갖는 방식은 사용자의 요구와 충돌한다. 로그인 식별 정보·메타데이터까지 모두 숨겨진다고 표현하지 않는다.
